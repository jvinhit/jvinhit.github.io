Hai pattern đầu tiên trả lời câu hỏi cơ bản nhất: *làm sao đóng gói trạng thái để nó không rò rỉ thành biến toàn cục*, và *làm sao đảm bảo một thứ chỉ tồn tại đúng một thể hiện* (kết nối WebSocket, store cấu hình, cache). Cả hai đều quen thuộc nhưng dễ dùng sai.

---

## 1. Vấn đề: biến toàn cục là cái bẫy

Khi nhiều phần code cùng đọc/ghi một biến toàn cục, bạn mất khả năng kiểm soát: ai đổi nó, khi nào, và một lỗi ở nơi này làm hỏng nơi khác.

```ts
// ❌ state exposed globally — anyone can overwrite it
window.currentUser = null;
window.apiToken = 'abc';
// ...3000 lines later, another module accidentally: window.apiToken = undefined;
```

Module pattern giải quyết bằng cách **giấu trạng thái sau một closure**, chỉ lộ ra những gì cần.

---

## 2. Module pattern

### Cách cổ điển: IIFE + closure

Trước khi có ES modules, người ta dùng hàm tự gọi (IIFE) để tạo phạm vi riêng:

```ts
const counter = (() => {
  let count = 0; // private — nothing outside can touch it

  return {
    increment: () => ++count,
    decrement: () => --count,
    get value() {
      return count; // read-only via getter
    },
  };
})();

counter.increment();
counter.value; // 1
// counter.count → undefined: count is protected
```

### Cách hiện đại: ES modules

ES modules **chính là** module pattern ở cấp ngôn ngữ: mọi thứ trong file là riêng tư trừ khi `export`. Đây là cách bạn nên dùng mặc định.

```ts
// counter.ts — count is hidden, only behavior is exported
let count = 0;
export const increment = () => ++count;
export const decrement = () => --count;
export const getValue = () => count;
```

Một điểm quan trọng và hay bị quên: **module ES được cache theo định danh** — import cùng một module ở nhiều nơi sẽ nhận **cùng một thể hiện**. Nghĩa là một module có state ở trên *đã là một singleton* rồi.

---

## 3. Singleton pattern

Singleton đảm bảo một class chỉ có **đúng một thể hiện** và cung cấp điểm truy cập chung. Hợp cho thứ vốn dĩ chỉ nên có một: kết nối realtime, store cấu hình, cache toàn app.

### Cách trực tiếp nhất ở frontend: một module có state

Vì module ES đã là singleton, thường bạn **không cần** class Singleton. Chỉ cần export một object đã khởi tạo:

```ts
// config.ts — every import receives this exact object
class AppConfig {
  private settings = new Map<string, unknown>();
  set(key: string, value: unknown) { this.settings.set(key, value); }
  get<T>(key: string): T | undefined { return this.settings.get(key) as T | undefined; }
}

export const config = new AppConfig(); // created ONCE, export the instance
```

### Khi cần lazy + bảo vệ chống tạo nhiều lần

Đôi khi bạn muốn khởi tạo trễ (chỉ tạo khi dùng lần đầu) và đảm bảo cứng rằng không ai tạo thêm:

```ts
class WebSocketClient {
  private static instance: WebSocketClient | null = null;
  private socket: WebSocket;

  private constructor(url: string) {
    this.socket = new WebSocket(url); // private constructor → no new from outside
  }

  static getInstance(url: string): WebSocketClient {
    // create on first call, return the same instance afterward (lazy singleton)
    if (!WebSocketClient.instance) {
      WebSocketClient.instance = new WebSocketClient(url);
    }
    return WebSocketClient.instance;
  }

  send(data: unknown) { this.socket.send(JSON.stringify(data)); }
}

const ws = WebSocketClient.getInstance('wss://example.com'); // always the same connection
```

`private constructor` là chìa khóa: nó ngăn `new WebSocketClient()` từ bên ngoài, ép mọi người đi qua `getInstance`.

## 4. Vì sao Singleton dễ thành phản pattern

Singleton bị mang tiếng xấu là có lý do. Ở frontend, hãy cẩn thận với ba vấn đề:

### Trạng thái toàn cục ẩn → khó test

Singleton là trạng thái chia sẻ toàn app. Trong test, thể hiện không được reset giữa các test case → test này ảnh hưởng test kia. Khắc phục: cho phép reset, hoặc tốt hơn là **tiêm phụ thuộc** (Dependency Injection, Phần 11) thay vì truy cập singleton trực tiếp.

```ts
// add an escape hatch so tests can reset state
class WebSocketClient {
  static reset() { WebSocketClient.instance = null; } // test-only
}
```

### Singleton + SSR = rò rỉ giữa các request

Đây là cái bẫy chí mạng trong Next.js/SSR: một singleton ở module-level **bị chia sẻ giữa các request của nhiều người dùng** trên server. Lưu `currentUser` vào singleton trên server có thể khiến user A thấy dữ liệu user B. Trên server, trạng thái theo-người-dùng phải nằm trong phạm vi request, không phải singleton toàn cục.

### Coupling chặt

Mọi nơi gọi `Singleton.getInstance()` đều bị **buộc cứng** vào lớp đó. Đổi cài đặt = sửa khắp nơi. DI giúp đảo ngược điều này (Phần 11, nguyên lý D của SOLID).

---

## 5. Lựa chọn thực dụng ở frontend hiện đại

| Nhu cầu | Dùng |
|---------|------|
| Static constants/config | ES module `export const` |
| Shared state in app (client) | store (Zustand/Redux) or module with state |
| Single connection/resource | lazy Singleton (watch SSR) |
| State that needs easy testing/replacement | DI via context/props, avoid direct singleton |

> Ở client-only app, một module có state thường đủ và rõ ràng hơn class Singleton. Dùng store khi cần reactivity (component re-render khi state đổi) — đó là chủ đề Phần 10.

---

## Tóm tắt

- **Module pattern** giấu trạng thái sau closure; **ES modules** là module pattern ở cấp ngôn ngữ và đã được cache (mỗi import = cùng thể hiện).
- **Singleton** đảm bảo một thể hiện duy nhất; `private constructor` + `getInstance` cho bản lazy.
- Singleton dễ thành phản pattern: **khó test**, **rò rỉ giữa request khi SSR**, **coupling chặt**.
- Ở frontend hiện đại: ưu tiên module export const / store; dùng singleton có ý thức, ưu tiên DI khi cần test/thay thế.

**Phần tiếp theo:** Observer & Pub/Sub — nền tảng của reactivity, event bus và signals.
