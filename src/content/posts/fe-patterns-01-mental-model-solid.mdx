Nhiều người hiểu sai "design pattern" theo hai hướng cực đoan: một số coi đó là kiến thức Java cũ kỹ không liên quan tới frontend hiện đại; số khác nhồi pattern vào mọi nơi, biến code đơn giản thành mê cung class. Cả hai đều sai.

Pattern là **lời giải lặp đi lặp lại cho các vấn đề lặp đi lặp lại** về tổ chức code. Frontend dùng chúng mọi ngày — chỉ là núp dưới tên React, Redux, hay Web API. Series này (12 phần) gọi tên chúng, cho thấy *vấn đề* mỗi pattern giải quyết, và quan trọng nhất: *khi nào KHÔNG nên dùng*.

## 1. Pattern là gì — và KHÔNG phải là gì

**Là**: một tên gọi chung cho một cách tổ chức code đã được chứng minh, giúp ta giao tiếp ("chỗ này dùng Strategy" gói gọn cả một ý tưởng) và tránh phát minh lại bánh xe.

**Không phải**: một mục tiêu. Bạn không "viết code để dùng pattern". Bạn gặp một vấn đề, và pattern là *một trong những* cách giải. Nhồi pattern khi chưa có vấn đề = over-engineering.

> Quy tắc thực dụng: pattern là **công cụ rút gọn sự phức tạp khi nó đã xuất hiện**, không phải lớp áo mặc sẵn cho code chưa phức tạp. Khi nghi ngờ, hãy chọn giải pháp đơn giản nhất chạy được, và chỉ refactor sang pattern khi nỗi đau thực sự đến (trùng lặp lần thứ ba, thay đổi lan rộng, khó test).

## 2. Ba nhóm pattern kinh điển

Bộ "Gang of Four" chia 23 pattern thành ba nhóm. Hiểu nhóm giúp bạn định vị nhanh:

- **Creational (khởi tạo)** — *làm sao tạo object*. Factory (Phần 4), Singleton (Phần 2), Builder. Frontend: tạo client API theo môi trường, tạo store.
- **Structural (cấu trúc)** — *làm sao ghép object/thành phần*. Adapter, Facade (Phần 7), Decorator, Proxy (Phần 8). Frontend: bọc SDK bên thứ ba, HOC, reactive proxy.
- **Behavioral (hành vi)** — *làm sao object giao tiếp & phân chia trách nhiệm*. Observer (Phần 3), Strategy (Phần 5), Command (Phần 6), State. Frontend: reactivity, validation hoán đổi, undo/redo.

Frontend còn có **pattern riêng của mình** mà GoF không có: Compound Components, Render Props, Custom Hooks (Phần 9), Flux (Phần 10). Ta sẽ coi chúng ngang hàng với pattern kinh điển.

## 3. SOLID qua lăng kính frontend

SOLID là năm nguyên lý thiết kế hướng đối tượng, nhưng tinh thần của chúng áp dụng thẳng cho component và hook. Đây là "kim chỉ nam" để biết *khi nào* một pattern đáng dùng.

### một trách nhiệm

Mỗi component/hook/module nên có **một lý do để thay đổi**. Một component vừa fetch data, vừa format, vừa render, vừa quản lý form là vi phạm — đổi cách fetch thì đụng cả render.

```tsx
// ❌ One component owns everything: fetch + transform + render + filter
function UserList() {
  const [users, setUsers] = useState([]);
  useEffect(() => { fetch('/api/users').then(/* ...transform... */); }, []);
  // ...filter, sort, render all in one place
}

// ✅ Split responsibilities: hook handles data, component handles display
function useUsers() { /* fetch + cache + transform */ }
function UserList() {
  const { users } = useUsers(); // only cares about rendering
  return <ul>{users.map((u) => <UserRow key={u.id} user={u} />)}</ul>;
}
```

Đây cũng là nguyên tắc "tách logic khỏi UI" — đặt fetch/format/business logic vào hook hoặc `lib/`, để component tập trung vào trình bày.

### mở để mở rộng, đóng để sửa đổi

Thêm tính năng mới nên là **thêm code mới**, không phải sửa code cũ (dễ gây hồi quy). Strategy (Phần 5) và Factory (Phần 4) là cách điển hình đạt điều này: thêm một "chiến lược" mới mà không động vào logic đang chạy.

### thay thế được

Một component "con" (biến thể) phải dùng được ở mọi nơi component "cha" dùng, không gây bất ngờ. Ví dụ: một `<IconButton>` nên chấp nhận mọi prop mà `<button>` chấp nhận (qua `...rest`), nếu không nó "phá hợp đồng" và gây lỗi khi thay thế.

### tách giao diện nhỏ

Đừng bắt component nhận một prop "khổng lồ" mà nó chỉ dùng một phần. Props nhỏ, tập trung sẽ dễ tái dùng và dễ test hơn.

```tsx
// ❌ accepts the whole user object when only name + avatar are needed
function Avatar({ user }: { user: FullUser }) { return <img src={user.avatarUrl} alt={user.name} />; }

// ✅ only takes what's needed → reusable from any data source
function Avatar({ src, alt }: { src: string; alt: string }) { return <img src={src} alt={alt} />; }
```

### đảo phụ thuộc

Module cấp cao không nên phụ thuộc trực tiếp vào chi tiết cấp thấp; cả hai nên phụ thuộc vào **trừu tượng**. Frontend: component không gọi thẳng `fetch`, mà nhận một `apiClient` qua context/props — nhờ vậy test thay bằng mock dễ dàng (Phần 11 bàn DI kỹ).

## 4. Một khung quyết định: có nên dùng pattern không?

Trước khi áp một pattern, hỏi:

1. **Vấn đề đã xuất hiện thật chưa?** (trùng lặp lần 3, thay đổi lan rộng, khó test) — hay tôi đang đoán trước tương lai?
2. **Pattern này làm code dễ đọc hơn hay khó hơn** với người tiếp theo?
3. **Có cách đơn giản hơn không?** Một hàm thuần, một hook nhỏ thường đủ.
4. **Chi phí trừu tượng có đáng không?** Mỗi lớp trừu tượng là một thứ phải hiểu khi debug.

> Nguyên tắc của series: *ưu tiên giải pháp đơn giản; chỉ dùng pattern khi nó cắt giảm sự phức tạp thực sự đang có, không phải sự phức tạp tưởng tượng.* (Đúng tinh thần "no over-engineering".)

## 5. Cách đọc 11 phần còn lại

Mỗi phần sau theo cùng một khuôn để bạn dễ so sánh:

1. **Vấn đề** — đoạn code "đau" mà pattern giải quyết.
2. **Pattern** — cài đặt TypeScript/React rõ ràng.
3. **Ở frontend** — pattern này thực ra đã nằm ở đâu (thư viện, Web API).
4. **Khi nào KHÔNG dùng** — cạm bẫy và over-engineering.

## Tóm tắt

- Pattern là **lời giải có tên cho vấn đề lặp lại**, không phải mục tiêu. Đừng nhồi khi chưa có vấn đề.
- Ba nhóm: **Creational** (tạo), **Structural** (ghép), **Behavioral** (giao tiếp) — cộng các pattern riêng của frontend.
- **SOLID** là kim chỉ nam: một trách nhiệm, mở rộng không sửa, thay thế được, giao diện nhỏ, đảo phụ thuộc.
- Luôn hỏi "vấn đề đã thật chưa?" và "có cách đơn giản hơn không?" trước khi áp pattern.

**Phần tiếp theo:** Module & Singleton — đóng gói trạng thái và đảm bảo "chỉ một thể hiện" mà không tạo biến toàn cục bừa bãi.
