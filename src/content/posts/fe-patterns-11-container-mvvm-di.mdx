Ba pattern cuối cùng trước capstone đều xoay quanh một ý tưởng: **tách "cái gì hiển thị" khỏi "logic đằng sau"**, và **không buộc cứng code vào phụ thuộc cụ thể**. Kết quả là code dễ đọc, dễ test, dễ thay thế — đúng tinh thần SOLID ở Phần 1.

---

## 1. Container / Presentational

Pattern kinh điển của React: chia component thành hai loại.

- **Presentational (trình bày)**: chỉ nhận props và render. Không biết dữ liệu từ đâu, không có state nghiệp vụ. Dễ tái dùng, dễ test, dễ đưa vào Storybook.
- **Container (chứa)**: lo lấy dữ liệu, state, side-effect; truyền xuống presentational.

```tsx
// Presentational: pure render, doesn't know the data source (Single Responsibility)
function UserCard({ name, email, onDelete }: { name: string; email: string; onDelete: () => void }) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{email}</p>
      <button onClick={onDelete}>Delete</button>
    </div>
  );
}

// Container: handles logic + data, passes down to presentational
function UserCardContainer({ id }: { id: string }) {
  const { data: user } = useFetch<User>(`/api/users/${id}`); // hook from Part 9
  const remove = () => deleteUser(id);
  if (!user) return <Skeleton />;
  return <UserCard name={user.name} email={user.email} onDelete={remove} />;
}
```

> Với hook ra đời, ranh giới này mềm hơn xưa — thường ta đặt logic vào **hook** thay vì một container component riêng. Nhưng tinh thần vẫn giá trị: **giữ component trình bày "ngu" và thuần**, để chúng dễ test và tái dùng. Đây cũng là cách phân tách của project này: helper/format/fetch ở `lib/`, component lo render.

## 2. MVVM qua lăng kính hook

MVVM (Model–View–ViewModel) đến từ thế giới WPF/Angular, nhưng ánh xạ rất tự nhiên vào React:

- dữ liệu & nghiệp vụ (API client, store, entity).
- component render (presentational).
- cầu nối — biến model thành thứ view cần, lo state UI. **Trong React, custom hook chính là ViewModel**.

```ts
// ViewModel: bundles all state + behavior for the search screen into one hook
function useProductSearch() {
  const [query, setQuery] = useState('');
  const [sort, setSort] = useState<'price' | 'name'>('name');
  const { data: products = [] } = useFetch<Product[]>('/api/products');

  // derived values belong to the ViewModel, not the View
  const visible = useMemo(() => {
    const filtered = products.filter((p) => p.name.toLowerCase().includes(query.toLowerCase()));
    return [...filtered].sort((a, b) => (sort === 'price' ? a.price - b.price : a.name.localeCompare(b.name)));
  }, [products, query, sort]);

  return { query, setQuery, sort, setSort, visible }; // ViewModel interface for the View
}
```

```tsx
// View: only wires ViewModel to UI, no business logic
function ProductSearch() {
  const vm = useProductSearch();
  return (
    <>
      <input value={vm.query} onChange={(e) => vm.setQuery(e.target.value)} />
      <select value={vm.sort} onChange={(e) => vm.setSort(e.target.value as 'price' | 'name')}>
        <option value="name">Name</option>
        <option value="price">Price</option>
      </select>
      <ul>{vm.visible.map((p) => <li key={p.id}>{p.name}</li>)}</ul>
    </>
  );
}
```

Lợi ích: **test ViewModel mà không cần render** (test hook bằng `@testing-library/react`'s `renderHook`), và View trở nên cực mỏng. Logic phức tạp (lọc, sort, dẫn xuất) nằm gọn một nơi.

## 3. Dependency Injection: đảo ngược phụ thuộc

Đây là nguyên lý D của SOLID (Phần 1) thành hình. Thay vì component **tự tạo** hoặc **gọi thẳng** phụ thuộc (API client, logger), ta **tiêm** chúng từ ngoài. Nhờ vậy, test có thể thay bằng bản giả, và đổi cài đặt không cần sửa component.

```tsx
// ❌ component hard-wired to fetch + a specific endpoint → hard to test, hard to swap
function UserList() {
  const [users, setUsers] = useState<User[]>([]);
  useEffect(() => {
    fetch('https://api.prod.com/users').then((r) => r.json()).then(setUsers);
  }, []);
  // tests must mock global fetch — fragile
}
```

DI ở React thường làm qua **Context** — cung cấp phụ thuộc ở trên cây, lấy ra ở dưới:

```tsx
// 1. Define the abstraction (interface), not a concrete implementation
interface ApiClient {
  getUsers(): Promise<User[]>;
}

// 2. Context holds the dependency
const ApiContext = createContext<ApiClient | null>(null);

function useApi(): ApiClient {
  const api = useContext(ApiContext);
  if (!api) throw new Error('useApi must be used inside <ApiProvider>');
  return api;
}

// 3. Component depends on the ABSTRACTION, not on any specific implementation
function UserList() {
  const api = useApi();
  const { data: users = [] } = useQuery({ queryKey: ['users'], queryFn: () => api.getUsers() });
  return <ul>{users.map((u) => <li key={u.id}>{u.name}</li>)}</ul>;
}
```

```tsx
// 4. Production injects the real client; tests inject a fake — WITHOUT editing UserList
<ApiContext.Provider value={realApiClient}><UserList /></ApiContext.Provider>;

// in tests:
const fakeApi: ApiClient = { getUsers: async () => [{ id: '1', name: 'Test' } as User] };
<ApiContext.Provider value={fakeApi}><UserList /></ApiContext.Provider>;
```

DI biến component từ "tự đi lấy đồ" thành "được trao đồ" — đây là chìa khóa để test không cần mock toàn cục, và để hoán đổi cài đặt (ghép đẹp với Adapter ở Phần 7).

## 4. Liên kết các pattern lại

Để ý cách các pattern khớp nhau ở tầng kiến trúc này:

- **DI** cung cấp **Adapter** (Phần 7) qua Context → app phụ thuộc trừu tượng.
- **ViewModel (hook)** dùng các phụ thuộc được tiêm, phơi state cho **View (presentational)**.
- State bên trong ViewModel có thể theo **Flux/State Machine** (Phần 10).
- View có thể là **Compound Components** (Phần 9).

Pattern không sống đơn lẻ — một màn hình tốt là sự phối hợp của nhiều pattern, mỗi cái lo một mối quan tâm.

---

## 5. Khi nào KHÔNG dùng

- **DI qua Context cho mọi thứ** → "context hell" và re-render thừa. Chỉ tiêm những phụ thuộc *thực sự cần thay thế/test* (API client, config, theme), không tiêm hàm tiện ích vặt.
- **Tách container/presentational máy móc** cho component bé xíu → thừa file, thừa indirection.
- **MVVM nặng nề** cho màn hình tĩnh → một component đơn giản là đủ.
- Nguyên tắc xuyên suốt: trừu tượng để *giảm* phức tạp đang có, không phải để *trưng bày* kiến trúc.

---

## Tóm tắt

- **Container/Presentational** tách logic khỏi render; thời hook, logic thường vào hook nhưng tinh thần "component trình bày thuần" vẫn quý.
- **MVVM**: custom hook đóng vai **ViewModel** — gom state + dẫn xuất, để View cực mỏng và test được không cần render.
- **Dependency Injection** (qua Context) đảo ngược phụ thuộc: component phụ thuộc *trừu tượng*, test thay bằng bản giả mà không sửa UI — ghép đẹp với Adapter.
- Các pattern phối hợp, không sống đơn lẻ; chỉ trừu tượng khi nó giảm phức tạp thật.

**Phần tiếp theo:** Capstone — refactor một feature rối bằng nhiều pattern, từng bước một.
