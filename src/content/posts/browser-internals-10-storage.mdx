Phần 8–9 đã đi qua bộ nhớ trong renderer và byte trên dây. Phần này về **lưu trữ client bền vững** — API app dùng để nhớ state qua reload, offline, và cache response lập trình được.

Mọi cơ chế lưu trữ chia sẻ một quy tắc cứng: dữ liệu theo **origin** (`scheme + host + port`). `https://app.example.com` không đọc được dữ liệu `https://other.example.com` — và ngày càng nhiều, **ngữ cảnh third-party** bị partition thêm vì privacy. Chọn sai API có nghĩa chặn luồng chính, vượt quota, hoặc rò dữ liệu trên mọi HTTP request.

---

## 1. Mô hình lưu trữ theo origin

**Origin** là bộ `(protocol, hostname, port)`. Mọi API lưu trữ chính phân vùng theo origin — không theo tab, không theo path.

```text
https://shop.example.com:443   ← origin A
  ├─ localStorage (A)
  ├─ IndexedDB database "orders" (A)
  ├─ Cache API "v1-static" (A)
  └─ Cookies with Domain=shop.example.com (A)

https://cdn.example.com:443    ← origin B (separate bucket)
  └─ its own isolated storage
```

Trình duyệt hiện đại cũng **partition storage** (CHIPS, loại bỏ cookie third-party): iframe từ `tracker.example` nhúng trên `shop.example` có thể có cookie jar **partitioned** theo site top-level, không phải bucket third-party dùng chung. Phần 11 gắn với mô hình bảo mật.

> Hai trang cùng origin thì dùng chung storage — kể cả giữa các tab. Dùng sự kiện `storage` (cho `localStorage`) hoặc `BroadcastChannel` để đồng bộ giữa tab.

---

## 2. So sánh cơ chế lưu trữ

| Cơ chế | Gửi kèm HTTP? | Giới hạn | Kiểu API | Kiểu dữ liệu |
|-----------|--------------------------|------------|-----------|--------------------------------------------------|
| **Cookies** | Yes — every matching request | ~4 KB per cookie | Sync (`document.cookie`) | Chuỗi |
| **sessionStorage** | No | ~5–10 MB per origin | Sync | Chuỗi |
| **localStorage** | No | ~5–10 MB per origin | Sync | Chuỗi |
| **IndexedDB** | No | Large (disk quota) | Async (transactions) | Có cấu trúc |
| **Cache API** | No | Shares quota with IDB | Async | `Request` / `Response` pairs |

Bảng là cây quyết định trong một nhìn: cần token session server đọc được → cookie; pref UI nhỏ → `localStorage`; dataset offline lớn → IndexedDB; chặn fetch offline → Cache API + Service Worker.

## 3. Cookie: nhỏ, tự động, server thấy được

**HTTP cookie** là cặp tên-giá trị server đặt qua `Set-Cookie` và trình duyệt gắn vào request sau qua header `Cookie`. Chúng là lưu trữ client gốc của web — và cạm bẫy lớn nhất là **gửi tự động**.

```http
Set-Cookie: session=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=604800
```

Thuộc tính quan trọng:

| Thuộc tính | Mục đích |
|-----------|---------------------|
| **`HttpOnly`** | JS không đọc — giảm đánh cắp token XSS |
| **`Secure`** | Chỉ gửi qua HTTPS |
| **`SameSite=Lax/Strict/None`** | Kiểm soát gửi cross-site (giảm CSRF) |
| **`Max-Age` / `Expires`** | Thời hạn |
| **`Domain` / `Path`** | Phạm vi gắn vào request |

Cookie **nhỏ** (~4 KB mỗi cái, số lượng giới hạn mỗi domain) và **đồng bộ** từ JS qua `document.cookie` — vụng về cho việc hơn flag đơn giản. Ưu tiên cookie session **`HttpOnly`** cho auth; không bao giờ lưu payload lớn trong cookie (phình mọi request).

## 4. Web Storage: localStorage và sessionStorage

**Web Storage API** có hai kho cùng origin:

- **`localStorage`** — bền đến khi xóa tường minh; sống sót restart trình duyệt.
- **`sessionStorage`** — theo **ngữ cảnh duyệt top-level** (tab/cửa sổ); xóa khi đóng tab.

Cả hai **đồng bộ** và **chỉ chuỗi**:

```js
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme'); // blocks main thread while disk I/O runs

// Objects must be serialized manually
localStorage.setItem('prefs', JSON.stringify({ density: 'compact' }));
```

### Vì sao storage đồng bộ nguy hiểm trên luồng chính

Đọc/ghi `localStorage` có thể chặn luồng chính khi trình duyệt chạm đĩa — đặc biệt lần truy cập đầu hoặc giá trị lớn. Trên trang đang layout và JS (Phần 7), đọc storage chậm góp vào jank **INP**. Giữ giá trị nhỏ; hoãn đọc không gấp; không dùng Web Storage như database.

> **`localStorage`** không chia sẻ với worker. Dữ liệu có cấu trúc lớn hơn dùng **IndexedDB**.

## 5. IndexedDB: database client-side thật sự

**IndexedDB** là object store giao dịch, async, cho dữ liệu có cấu trúc quy mô lớn. Khác Web Storage, nó chạy ngoài đường đồng bộ quan trọng và hỗ trợ **index**, **cursor**, lưu **Blob**/`File`, và **migration schema có version**.

```js
function openDb() {
  return new Promise((resolve, reject) => {
    const req = indexedDB.open('app-db', 1);

    req.onupgradeneeded = () => {
      const db = req.result;
      const store = db.createObjectStore('notes', { keyPath: 'id' });
      store.createIndex('byUpdated', 'updatedAt');
    };

    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}

async function saveNote(note) {
  const db = await openDb();
  return new Promise((resolve, reject) => {
    const tx = db.transaction('notes', 'readwrite');
    tx.objectStore('notes').put(note);
    tx.oncomplete = () => resolve(undefined);
    tx.onerror = () => reject(tx.error);
  });
}
```

Khái niệm cần nắm:

- **Database** → **object store** (như bảng) → record key theo key path hoặc out-of-line key.
- **Transaction** là đơn vị công việc — tự commit khi thành công, abort khi lỗi; không chia sẻ qua khoảng async bừa bãi.
- **Version** — tăng `version` trong `open()` và migrate trong `onupgradeneeded`.

Thư viện như **`idb`** bọc API dài dòng; app React, **`Dexie.js`** thêm lớp thân thiện. IndexedDB là default đúng cho app offline-first, cache lớn, và nội dung user tạo.

## 6. Cache API và Service Worker

**Cache API** lưu cặp **`Request`/`Response`** — cùng hình dạng pipeline fetch dùng (Phần 9). Thiết kế để dùng với **Service Worker**, proxy mạng lập trình được trên luồng nền.

### Lifecycle Service Worker

```text
Register sw.js
    │
    ▼
install  → precache static shell (cache.addAll)
    │
    ▼
activate → delete old caches (cache.delete)
    │
    ▼
fetch    → intercept network requests (event.respondWith)
```

```js
// sw.js (simplified)
const CACHE = 'v1-shell';

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE).then((cache) => cache.addAll(['/', '/app.css', '/app.js']))
  );
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(keys.filter((k) => k !== CACHE).map((k) => caches.delete(k)))
    )
  );
});

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached ?? fetch(event.request))
  );
});
```

Trang bị **controlled** bởi Service Worker chỉ sau đăng ký **và** navigation kích hoạt — lần visit đầu có thể vẫn chỉ mạng.

### Chiến lược cache phổ biến

| Chiến lược | Hành vi | Phù hợp |
|----------|----------|-------------------------------------|
| **Cache-first** | Cache → network on miss | Asset tĩnh, app shell |
| **Network-first** | Network → cache fallback | Dữ liệu API cần tươi |
| **Stale-while-revalidate** | Return cache immediately, update in background | Nội dung bán tĩnh |
| **Network-only** | Never cache | Endpoint nhạy cảm auth |

Cạm bẫy: cache HTML hung hăng phục vụ phiên bản cũ; `cache.put()` không giới hạn cạn quota; quên `skipWaiting()` / `clients.claim()` trễ control. Luôn version tên cache và xóa bucket cũ khi activate.

## 7. Quota, eviction, và persistence

Storage không vô hạn. Trình duyệt cấp mỗi origin một **quota** — phần đĩa khả dụng — dùng chung IndexedDB, Cache API, và (một số trình duyệt) API khác.

```js
const { usage, quota } = await navigator.storage.estimate();
console.log(`Using ${usage} of ${quota} bytes`);
```

Hai chế độ persistence quan trọng:

- **Best-effort (mặc định)** — trình duyệt **có thể evict** dữ liệu khi áp lực storage (LRU giữa origin).
- **Persistent** — yêu cầu qua `navigator.storage.persist()`; được cấp nếu site đã cài, có quyền, hoặc user tương tác đáng kể.

Chế độ duyệt riêng dùng profile tạm — giả định dữ liệu có thể mất. Không bao giờ coi client là nguồn sự thật duy nhất cho dữ liệu không thay thế được.

## 8. Privacy: partitioning và storage third-party

Cookie third-party — đặt bởi tracker, quảng cáo, widget nhúng — cho phép theo dõi cross-site hàng thập kỷ. Trình duyệt đang **loại bỏ dần** và **partition** storage theo site top-level:

- **Storage Partitioning** — `tracker.com` trong iframe trên `shop.com` có bucket riêng với `tracker.com` trên `news.com`.
- **CHIPS** — cookie third-party nhỏ theo site top-level.
- **First-party sets** — ngoại lệ hạn chế cho domain sở hữu (chính sách khác nhau theo trình duyệt).

Với kỹ sư: auth và cá nhân hóa nên ở **origin first-party**; embed cross-site không nên dựa storage third-party dùng chung. Dùng cookie **`SameSite`**, redirect OAuth trên domain riêng, và **`postMessage`** cho giao tiếp cross-frame.

---

## 9. Khi nào dùng cái nào

| Nhu cầu | Dùng | Tránh |
|------|-----|--------|
| Session token for server auth | `HttpOnly` **cookie** | `localStorage` (XSS đọc được) |
| Theme / language preference | **`localStorage`** | Cookie (gửi mọi request) |
| Form draft for one tab session | **`sessionStorage`** | Cookies |
| Offline docs, 10k+ records, binary blobs | **IndexedDB** | `localStorage` (size + sync) |
| Offline shell + cached assets | **Cache API** + **Service Worker** | Manual IDB of Response bodies |
| "Maybe next page" assets | HTTP **`prefetch`** (Part 9) | Cache API |

Nền tảng cho nhiều lớp — HTTP cache (tự động, Phần 9), Cache API (lập trình), IndexedDB (state app có cấu trúc) — xếp chồng có chủ đích, không cùng lúc cho cùng byte.

---

## Tóm tắt

- Mọi storage **theo origin**; trình duyệt hiện đại **partition** ngữ cảnh third-party vì privacy.
- **Cookie** nhỏ, tự gửi, server đọc được — dùng auth session với `HttpOnly`/`Secure`/`SameSite`.
- **localStorage/sessionStorage** đồng bộ và chỉ chuỗi — ổn pref nhỏ, nguy hiểm dữ liệu lớn hoặc đường nóng.
- **IndexedDB** async, lớn, có cấu trúc — database client cho app offline-first.
- **Cache API** + **Service Worker** cho chặn fetch lập trình và chiến lược offline.
- Theo dõi **`navigator.storage.estimate()`**; yêu cầu storage **persistent** khi eviction hại UX.

**Phần tiếp theo:** Mô hình bảo mật — same-origin policy, CORS, CSP, và cách site isolation biến ranh giới tiến trình thành ranh giới bảo mật.
