## Đo đúng thứ

Hai con số người ta hay nhầm: **latency** và **throughput** liên quan nhưng tối ưu khác nhau.

**đừng bao giờ báo latency trung bình** — nó giấu nỗi đau. Báo **percentile**:

```text
p50 = 20ms   ← half of requests are faster than this (the "typical" user)
p95 = 80ms   ← the slow 5%
p99 = 400ms  ← the painful 1% — often where timeouts and rage-quits live
```

Senior theo dõi **p99**, cộng tỷ lệ lỗi và độ bão hòa. Khung hữu ích: **RED** cho service, **USE** cho tài nguyên.

```bash
# Load test so numbers reflect concurrency, not a single curl
npx autocannon -c 100 -d 20 http://localhost:3000/api/posts   # 100 conns, 20s
# k6 / artillery are great for scripted, multi-step scenarios
```

Vòng lặp senior: **load test → profile → sửa bottleneck lớn nhất → test lại**.

## Profiling — tìm bottleneck thật

Bắt đầu trong tiến trình với `perf_hooks` để đo thao tác thật:

```ts
import { performance, PerformanceObserver, monitorEventLoopDelay } from 'node:perf_hooks';

new PerformanceObserver((items) => {
  for (const e of items.getEntries()) console.log(`${e.name}: ${e.duration.toFixed(1)}ms`);
}).observe({ entryTypes: ['measure'] });

performance.mark('q-start');
await db.heavyQuery();
performance.measure('heavyQuery', 'q-start', performance.mark('q-end').name);

// Event-loop lag is THE Node health metric — rising lag means you're blocking
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => console.log(`loop p99 lag: ${(h.percentile(99) / 1e6).toFixed(1)}ms`), 5000);
```

Để có bức tranh đầy đủ, dùng profiler:

- chẩn đoán; flame graph; luồng async.
- profile CPU.
- flame graph nhanh; heap snapshot cho bộ nhớ.

Đọc flame graph đơn giản: **bề rộng = tổng thời gian trong hàm đó**. Cao nguyên rộng nhất là bottleneck — không phải hàm bạn *tưởng* là chậm.

## Đừng chặn event loop

Bug hiệu năng tai hại nhất không phải query chậm — mà là **việc CPU trên luồng chính**. Vòng đồng bộ, `JSON.parse` khổng lồ, crypto đồng bộ, hay regex thảm họa đóng băng *mọi* request đồng thời.

```ts
// ❌ Blocks the loop for everyone while it runs
const result = expensiveSyncComputation(hugeInput);

// ✅ Offload genuine CPU work to a worker thread (use a pool: piscina)
import Piscina from 'piscina';
const pool = new Piscina({ filename: new URL('./worker.js', import.meta.url).href });
const result = await pool.run(hugeInput);   // main loop stays responsive
```

Quy tắc: I/O → event loop; **CPU → worker thread**; lag event loop tăng là chuông báo.

## Tối ưu database

Database là bottleneck số 1 trong đa số API. Sổ tay senior:

1. diệt N+1 bằng eager loading; gộp bằng DataLoader.
2. index; xác minh bằng `EXPLAIN ANALYZE`.
3. chỉ chọn cột cần — `SELECT *` chuyển và giải mã dữ liệu bạn bỏ.
4. chỉnh pool — nhỏ quá đói, lớn quá ngợp DB.

```ts
// ✅ Eager loading + projection — one query, only the fields you use
const users = await User.findAll({
  attributes: ['id', 'email'],
  include: [{ model: Post, as: 'posts', attributes: ['id', 'title'] }],
});
```

## Caching — mọi tầng

Caching là đòn bẩy lớn nhất cho API đọc nhiều. Nghĩ theo tầng, rẻ nhất trước:

```text
client/CDN cache ─▶ HTTP cache (ETag/Cache-Control) ─▶ app memory (LRU)
      ─▶ Redis (shared) ─▶ database
   each layer you hit saves the cost of every layer below it
```

**Cache-aside** (mặc định) và **write-through** lo phần lớn:

```ts
async function getUserProfile(userId: string) {
  const key = `user:${userId}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);                       // hit
  const user = await User.findByPk(userId);                    // miss → DB
  await redis.set(key, JSON.stringify(user), 'EX', 3600);
  return user;
}
```

Thêm **LRU trong tiến trình** trước Redis cho key cực nóng, và **HTTP caching** để client/CDN bỏ qua server. Hai bài toán khó vẫn là **invalidation** và **stampede**.

## Mở rộng theo lõi — clustering & worker

Node mặc định chạy một lõi. Module `cluster` fork một worker mỗi lõi, chung cổng lắng nghe:

```ts
import cluster from 'node:cluster';
import { availableParallelism } from 'node:os';

if (cluster.isPrimary) {
  for (let i = 0; i < availableParallelism(); i++) cluster.fork();
  cluster.on('exit', (w) => { console.log(`worker ${w.process.pid} died`); cluster.fork(); });
} else {
  app.listen(3000);
}
```

Cái này nhân **throughput** xấp xỉ số lõi; PM2/orchestrator làm hộ ở prod. Phân biệt rõ: **cluster** = nhiều tiến trình cho throughput I/O; **worker thread** = đẩy CPU trong một tiến trình. Clustering **không** làm nhanh một request chậm.

## Bộ nhớ & GC — săn rò rỉ

V8 chia heap thành young (rẻ, thường) và old (đắt, hiếm). **Rò rỉ** là bộ nhớ vẫn được tham chiếu và trôi sang old mãi.

```ts
const m = process.memoryUsage();
console.log(`heapUsed ${(m.heapUsed / 1048576).toFixed(1)}MB rss ${(m.rss / 1048576).toFixed(1)}MB`);
```

Săn rò rỉ bằng **hai heap snapshot dưới tải**, rồi **diff** — vật thể lớn dần là rò rỉ. Thủ phạm thường gặp: cache/mảng không giới hạn, `setInterval`/listener bị quên, closure giữ vật thể lớn, `Map` khóa-object không dùng `WeakMap`.

> Mẹo V8 nhanh: giữ hình dạng object **đơn hình**; tránh `delete` trên object nóng; chốt `--max-old-space-size`.

## 9. Dự án thực hành

1. Baseline + profile: load test, ghi p50/p99, rồi clinic và tìm cao nguyên rộng nhất.

2. Sửa bottleneck DB: tái hiện N+1, sửa + thêm index, xác nhận.

3. Cache nhiều tầng: thêm cache-aside + LRU + ETag; đo p99 từng tầng và invalidation.

4. Đẩy CPU: chuyển endpoint nặng CPU sang piscina; chứng minh lag giảm.

5. Cluster & so sánh: chạy đơn vs cluster dưới tải và vẽ chênh lệch throughput.

6. Săn rò rỉ: tạo cache lớn dần, diff hai snapshot, rồi sửa.
