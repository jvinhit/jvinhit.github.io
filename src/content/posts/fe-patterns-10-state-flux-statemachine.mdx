Quản lý state là vấn đề khó nhất của frontend. Khi app lớn lên, state rải khắp nơi, đổi từ nhiều chỗ, và bug "tại sao nó lại ở trạng thái này?" trở nên thường xuyên. Hai pattern giúp thuần hóa: **luồng một chiều** (Flux/Redux) làm thay đổi state dễ truy vết, và **state machine** làm những trạng thái sai *không thể tồn tại*.

---

## 1. Vấn đề: state đổi từ mọi hướng

```tsx
// ❌ many loose boolean flags → meaningless state combinations can occur
const [isLoading, setIsLoading] = useState(false);
const [isError, setIsError] = useState(false);
const [data, setData] = useState(null);
// isLoading=true AND isError=true at the same time? data present on error? — nothing prevents it
```

Với 3 boolean ta có 8 tổ hợp, nhưng chỉ vài tổ hợp là hợp lệ. Phần còn lại là "trạng thái không thể xảy ra" mà code vẫn cho phép — nguồn của vô số bug UI.

---

## 2. Flux/Redux: luồng dữ liệu một chiều

Ý tưởng cốt lõi của Flux: state chỉ đổi theo **một chiều khép kín**, không cho ai sửa trực tiếp.

```text
   ┌──────────────────────────────────────────┐
   │                                          ▼
 Action ──→ Reducer (pure fn) ──→ New state ──→ View
   ▲                                              │
   └──────────────── dispatch ────────────────────┘
```

- object mô tả "có chuyện gì xảy ra" (không phải "làm gì").
- hàm thuần `(state, action) => state mới` — không side-effect, không mutate.
- giữ state, nhận `dispatch(action)`, thông báo view (Observer — Phần 3!).

Reducer thuần khiến mọi thay đổi state **dễ truy vết** (chỉ có một nơi đổi state) và **dễ test** (chỉ là hàm thuần input → output):

```ts
interface CartState {
  items: { id: string; qty: number }[];
}

type CartAction =
  | { type: 'add'; id: string }
  | { type: 'remove'; id: string }
  | { type: 'clear' };

// Pure function: same (state, action) always yields same result, touches nothing outside
function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case 'add': {
      const existing = state.items.find((i) => i.id === action.id);
      if (existing) {
        return { items: state.items.map((i) => (i.id === action.id ? { ...i, qty: i.qty + 1 } : i)) };
      }
      return { items: [...state.items, { id: action.id, qty: 1 }] };
    }
    case 'remove':
      return { items: state.items.filter((i) => i.id !== action.id) };
    case 'clear':
      return { items: [] };
  }
}
```

`useReducer` của React là Flux thu nhỏ ngay trong component; Redux/Zustand là cùng ý tưởng ở quy mô app. Lưu ý reducer **bất biến** (luôn trả state mới) — điều này khớp với memoization và undo-snapshot (Phần 6) và làm reconciliation hiệu quả (series thuật toán, Phần 5).

```tsx
function Cart() {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  return <button onClick={() => dispatch({ type: 'add', id: 'sku-1' })}>Add</button>;
}
```

## 3. State Machine: dập tắt trạng thái không thể xảy ra

Flux làm thay đổi *dễ truy vết*, nhưng chưa ngăn được *trạng thái sai*. **State machine** (máy trạng thái hữu hạn) giải quyết: định nghĩa tập **trạng thái hợp lệ** và **chuyển tiếp hợp lệ** giữa chúng. Mọi chuyển tiếp không khai báo đều bị cấm.

Thay vì 3 boolean rời rạc, ta mô hình hóa data fetching bằng **một** trạng thái có 4 giá trị rõ ràng:

```ts
type FetchState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T } // data ONLY exists on success
  | { status: 'error'; error: Error }; // error ONLY exists on error
```

Kiểu union này khiến TypeScript **không cho** truy cập `data` khi chưa `success` — trạng thái sai bị chặn ngay ở tầng kiểu. Một máy trạng thái tường minh hóa các chuyển tiếp:

```ts
type Event<T> =
  | { type: 'FETCH' }
  | { type: 'RESOLVE'; data: T }
  | { type: 'REJECT'; error: Error }
  | { type: 'RESET' };

// Transition table: from state X, event Y leads to state Z
function fetchMachine<T>(state: FetchState<T>, event: Event<T>): FetchState<T> {
  switch (state.status) {
    case 'idle':
      return event.type === 'FETCH' ? { status: 'loading' } : state;
    case 'loading':
      if (event.type === 'RESOLVE') return { status: 'success', data: event.data };
      if (event.type === 'REJECT') return { status: 'error', error: event.error };
      return state; // other events are ignored → no illegal jumps
    case 'success':
    case 'error':
      return event.type === 'RESET' ? { status: 'idle' } : state;
  }
}
```

```tsx
function UserProfile() {
  const [state, dispatch] = useReducer(fetchMachine<User>, { status: 'idle' });

  // render by status — never "loading + error" at the same time
  switch (state.status) {
    case 'idle': return <button onClick={() => dispatch({ type: 'FETCH' })}>Load</button>;
    case 'loading': return <Spinner />;
    case 'success': return <h1>{state.data.name}</h1>; // TS knows data exists
    case 'error': return <ErrorBox error={state.error} />; // TS knows error exists
  }
}
```

Đây là sức mạnh thật: **những trạng thái vô nghĩa trở thành không thể biểu diễn**. Bug "spinner hiện cùng lúc với lỗi" biến mất ở cấp thiết kế, không phải nhờ vá. Thư viện như XState đưa ý tưởng này lên đầy đủ (guard, side-effect, biểu đồ phân cấp).

## 4. Khi nào dùng cái nào

| Tình huống | Pattern |
|------------|---------|
| Simple, local state | plain `useState` |
| State with many related update paths | **Reducer / Flux** |
| App-wide shared state | store (Redux/Zustand — Flux + Observer) |
| Process with clear "modes" and constrained transitions | **State Machine** |
| Multi-step forms, checkout flows, realtime connections | **State Machine** (great fit) |

Hai pattern này **bổ trợ** nhau: state machine thường được hiện thực *bằng* một reducer (bảng chuyển tiếp), và đặt trong store theo luồng một chiều.

---

## 5. Khi nào KHÔNG dùng

- **Redux/store toàn cục cho mọi thứ** → over-engineering kinh điển. State server (data từ API) hợp với React Query/SWR hơn; state cục bộ dùng `useState`. Chỉ đưa vào store global thứ *thực sự* dùng chung nhiều nơi.
- **State machine cho toggle on/off** → một boolean là đủ; máy trạng thái cho cái quá đơn giản chỉ thêm nghi thức.
- Nhớ: chọn mức độ "nghi thức" tương xứng với độ phức tạp thực của state.

---

## Tóm tắt

- **Flux/Redux**: luồng một chiều `action → reducer thuần → state mới → view`, làm thay đổi state **dễ truy vết và dễ test**; reducer luôn **bất biến**.
- **State Machine**: định nghĩa trạng thái + chuyển tiếp hợp lệ; dùng union type để **trạng thái sai không thể biểu diễn** — diệt bug ở cấp thiết kế.
- Hai pattern bổ trợ: machine thường là một reducer, đặt trong store một chiều.
- Đừng nhồi mọi state vào store global; chọn mức nghi thức tương xứng độ phức tạp.
