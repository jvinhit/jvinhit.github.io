Tối ưu vi mô (ảnh, font, bundle) có trần. Đòn bẩy lớn nhất thường là **kiến trúc render** — bạn dựng HTML ở đâu (server hay client) và "tưới sống" (hydrate) ra sao. Phần này so sánh các chiến lược render qua lăng kính Core Web Vitals, để bạn chọn đúng cho từng loại trang thay vì theo trào lưu framework.

> Câu hỏi trung tâm: **HTML có nội dung tới mắt người dùng nhanh thế nào (LCP/TTFB)**, và **trang phản hồi tương tác nhanh thế nào (INP)**? Mỗi chiến lược đánh đổi hai điều này khác nhau.

---

## 1. Bốn cách dựng HTML

```text
CSR (Client-Side Rendering)
  Server gửi HTML rỗng + JS → JS dựng DOM trên client
  TTFB nhanh, LCP CHẬM (chờ JS tải+chạy), tốn CPU client

SSR (Server-Side Rendering)
  Server dựng HTML đầy đủ mỗi request → client hydrate
  LCP nhanh hơn (HTML có sẵn), TTFB phụ thuộc tốc độ server

SSG (Static Site Generation)
  Dựng HTML lúc BUILD → phục vụ tĩnh qua CDN
  TTFB & LCP nhanh nhất, nhưng nội dung tĩnh (rebuild để cập nhật)

ISR (Incremental Static Regeneration)
  SSG + tái sinh nền theo thời gian/nhu cầu
  Tốc độ của SSG + nội dung tươi hơn
```

| | TTFB | LCP | Nội dung động | CPU client |
|---|---|---|---|---|
| CSR | ⚡ | 🐢 | ✅ | cao |
| SSR | 🙂 | ⚡ | ✅ | vừa |
| SSG | ⚡ | ⚡ | ❌ (build-time) | vừa |
| ISR | ⚡ | ⚡ | 🙂 (gần thật) | vừa |

Quy tắc thô: nội dung tĩnh/ít đổi (blog, docs, marketing) → **SSG/ISR**; cá nhân hóa cao/dữ liệu tươi → **SSR**; app sau đăng nhập, SEO không quan trọng → **CSR** có thể chấp nhận.

## 2. Vấn đề hydration — "uncanny valley"

SSR/SSG cho HTML nhanh, nhưng trang *trông* xong mà chưa *tương tác được* cho tới khi JS tải xong và **hydrate** (gắn event listener, dựng lại state). Khoảng giữa đó người dùng bấm mà không có gì xảy ra → INP/TTI tệ.

```text
SSR truyền thống:
  [HTML hiện nhanh — LCP tốt] ──── [JS tải] ──── [hydrate CẢ trang] ── tương tác được
                                    người dùng bấm ở đây → không phản hồi (INP xấu)
```

Hydrate toàn trang nghĩa là tải + chạy lại *toàn bộ* JS component dù phần lớn trang là tĩnh. Đây là gốc rễ của nhiều vấn đề INP trong app SSR hiện đại.

---

## 3. Các kiểu hydration giảm chi phí

```text
① Islands (Astro, Fresh)
   Trang chủ yếu HTML tĩnh; chỉ vài "đảo" tương tác được hydrate.
   → JS tối thiểu, INP tốt cho trang nội dung.

② Partial / Selective hydration
   Hydrate component theo nhu cầu, không phải tất cả cùng lúc.

③ Progressive hydration
   Hydrate dần theo độ ưu tiên / khi cuộn tới (lazy).

④ Server Components (RSC)
   Component chạy CHỈ trên server, không gửi JS xuống client;
   chỉ Client Components mới hydrate. → giảm bundle đáng kể.
```

Tư duy chung: **gửi ít JS hơn, hydrate ít hơn**. Một trang blog không nên tải runtime của cả SPA. Islands và RSC là hai cách tiếp cận khác nhau cho cùng mục tiêu: trả HTML nhanh *và* giữ JS nhỏ.

## 4. Streaming SSR — trả HTML theo dòng

Thay vì chờ server dựng *toàn bộ* HTML rồi mới gửi (chặn TTFB), **streaming SSR** gửi phần trên (app shell, `<head>`, nội dung tĩnh) ngay, rồi stream tiếp phần cần dữ liệu khi sẵn sàng.

```text
Không streaming:  request → [chờ MỌI dữ liệu 600ms] → gửi cả HTML
Streaming:        request → gửi shell ngay (TTFB thấp)
                          → stream phần A khi query A xong
                          → stream phần B khi query B xong
```

React (`renderToPipeableStream`) + `<Suspense>` cho phép bao phần chậm trong Suspense: shell + nội dung nhanh hiện ngay (LCP tốt), phần chậm stream sau với fallback. Lợi cho cả TTFB lẫn LCP khi có dữ liệu chậm không đồng đều.

---

## 5. Ảnh hưởng tới từng Core Web Vital

```text
LCP:  SSG/SSR/streaming cho LCP tốt (HTML có nội dung sớm).
      CSR thường LCP xấu (chờ JS). fetchpriority + preload ảnh LCP (Part 14).

INP:  hydration nặng là kẻ thù số 1. Ít JS / islands / RSC / progressive
      hydration → INP tốt hơn. Chia nhỏ task (Part 16).

CLS:  SSR/SSG dễ bị CLS nếu hydration thay đổi layout, hoặc nội dung
      stream chèn vào đẩy layout. Đặt chỗ trước (reserve space), tránh
      chèn nội dung phía trên (Part 7).

TTFB: SSG/CDN nhanh nhất; SSR phụ thuộc server (cache, edge rendering);
      streaming cải thiện TTFB cảm nhận.
```

> Bẫy CLS với streaming: nội dung stream vào sau phải có chỗ đặt trước, nếu không nó đẩy phần đã hiện → layout shift. Streaming cải thiện LCP nhưng cần kỷ luật CLS.

---

## 6. Khung quyết định

```text
Trang nội dung tĩnh (blog/docs/landing)
  → SSG/ISR + islands. JS tối thiểu. LCP & INP đều tốt.

Trang động, SEO quan trọng (e-commerce, tin tức)
  → SSR/ISR + streaming + RSC. Cache mạnh ở edge.

App sau đăng nhập (dashboard), SEO không cần
  → CSR/SPA chấp nhận được, nhưng vẫn tối ưu bundle & INP.

Dữ liệu chậm không đồng đều
  → streaming SSR + Suspense (shell nhanh, phần chậm stream sau).
```

Đừng chọn kiến trúc theo framework "hot"; chọn theo **đặc tính trang** và **mục tiêu metric**. Một site thường trộn nhiều chiến lược (marketing = SSG, app = CSR, checkout = SSR).

---

## 7. Tóm tắt

- **CSR** TTFB nhanh nhưng LCP chậm (chờ JS); **SSR** LCP tốt, TTFB theo server; **SSG/ISR** nhanh nhất qua CDN, nội dung tĩnh/gần-tươi.
- **Hydration toàn trang** là gốc nhiều vấn đề INP: trang trông xong mà chưa bấm được.
- Giảm chi phí bằng **islands, partial/progressive hydration, Server Components (RSC)** — gửi ít JS, hydrate ít.
- **Streaming SSR + Suspense** trả shell ngay rồi stream phần chậm → tốt cho TTFB & LCP, nhưng cần đặt chỗ trước để tránh **CLS**.
- Chọn kiến trúc theo **đặc tính trang + mục tiêu metric**, không theo trào lưu; trộn nhiều chiến lược trong một site là bình thường.

**Phần tiếp theo:** INP deep & main-thread scheduling — Long Animation Frames (LoAF) API, `scheduler.postTask`/`yield`, `isInputPending`, và chia nhỏ tác vụ dài để giữ INP "Good".
