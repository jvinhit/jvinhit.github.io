## 1. Vì sao frontend cần thuật toán

Frontend có một ràng buộc mà backend không có gay gắt bằng: **ngân sách 16ms**. Để giữ 60fps, mỗi khung hình trình duyệt chỉ có khoảng 16.7ms để chạy JS, tính layout, paint và composite. Nếu JS của bạn ăn hết 16ms cho một vòng lặp `O(n²)`, không còn thời gian cho trình duyệt vẽ — và người dùng thấy giật.

Backend có thể "mua thêm thời gian" bằng cách scale ngang, cache ở tầng server, hay chạy job nền. Frontend thì chạy trên **máy của người dùng** — có thể là một chiếc điện thoại Android đời thấp. Bạn không kiểm soát phần cứng đó. Cách duy nhất để nhanh là **làm ít việc hơn**, và đó chính là chuyện của thuật toán.

Một vài tình huống quen thuộc và thuật toán ẩn sau:

- Ô tìm kiếm gọi API mỗi lần gõ phím → **rate limiting** (Phần 2).
- Lọc 50.000 sản phẩm khi người dùng gõ → **search index, binary search** (Phần 3).
- Render bảng 100.000 dòng → **ảo hóa** (Phần 4).
- React re-render chậm khi state đổi → **diffing & memoization** (Phần 5, 7).
- Menu phân cấp nhiều tầng → **duyệt cây** (Phần 6).

## 2. Big-O đọc theo kiểu thực dụng

Big-O mô tả **tốc độ tăng của thời gian (hoặc bộ nhớ) khi dữ liệu lớn dần**. Bạn không cần chứng minh toán học; bạn cần trả lời được một câu: *"Nếu dữ liệu tăng gấp đôi, công việc tăng bao nhiêu lần?"*

| Notation | Name | Double `n` means... | Frontend example |
|---------|---------|--------------------|----------------|
| `O(1)` | Hằng số | không đổi | `map.get(id)` |
| `O(log n)` | Logarit | +1 tăng thêm 1 bước | binary search in a sorted list |
| `O(n)` | Tuyến tính | gấp đôi | `array.filter`, a `for` loop |
| `O(n log n)` | Linearithmic | hơn gấp đôi chút | `array.sort` |
| `O(n²)` | Bậc hai | gấp **bốn** | two nested `for` loops |

Quy tắc thực dụng để ước lượng nhanh:

- Đếm số **vòng lặp lồng nhau** chạy theo `n`. Một vòng → `O(n)`. Hai vòng lồng → `O(n²)`.
- Bỏ hằng số và số hạng nhỏ: `O(2n + 5)` viết gọn là `O(n)`.
- `.map`, `.filter`, `.find`, `.includes`, `.indexOf` đều là `O(n)`. Gọi chúng *trong* một vòng lặp khác là cái bẫy `O(n²)` phổ biến nhất ở frontend.

Cái bẫy kinh điển — tìm phần tử trong mảng bên trong một vòng lặp:

```ts
// ❌ O(n²): each users iteration rescans all orders
function attachOrders(users: User[], orders: Order[]): UserWithOrders[] {
  return users.map((user) => ({
    ...user,
    orders: orders.filter((o) => o.userId === user.id), // O(n) inside O(n)
  }));
}
```

Sửa bằng cách đánh chỉ mục trước thành `Map` — đổi `O(n²)` thành `O(n)`:

```ts
// ✅ O(n): group orders by userId once, then O(1) lookups
function attachOrders(users: User[], orders: Order[]): UserWithOrders[] {
  const byUser = new Map<string, Order[]>();
  for (const order of orders) {
    const list = byUser.get(order.userId);
    if (list) list.push(order);
    else byUser.set(order.userId, [order]);
  }
  return users.map((user) => ({ ...user, orders: byUser.get(user.id) ?? [] }));
}
```

Với 1.000 user và 1.000 order, bản `O(n²)` làm ~1.000.000 phép so sánh; bản `O(n)` làm ~2.000. Đó là khác biệt giữa "mượt" và "đơ".

## 3. Cấu trúc dữ liệu là một nửa của thuật toán

Phần lớn việc tối ưu frontend không phải viết thuật toán cao siêu, mà là **chọn đúng cấu trúc dữ liệu** để thao tác trở thành `O(1)` hoặc `O(log n)`.

| Task | With an array it's... | Use this instead |
|--------------|------------------|-----------------------|
| Kiểm tra đã tồn tại chưa | `O(n)` (`includes`) | `Set` → `O(1)` |
| Tra cứu theo khóa | `O(n)` (`find`) | `Map` / object → `O(1)` |
| Lấy phần tử ưu tiên cao nhất | `O(n)` | Heap / priority queue → `O(log n)` |
| Tìm trong dữ liệu đã sort | `O(n)` | Binary search → `O(log n)` |

`Set` và `Map` là hai cấu trúc bạn sẽ dùng nhiều nhất. Ví dụ chọn nhiều dòng trong bảng:

```ts
// ❌ selectedIds is an array → toggle must scan the whole thing
const isSelected = selectedIds.includes(rowId); // O(n)

// ✅ selectedIds is a Set → toggle and check are both O(1)
const selected = new Set<string>();
const isSelected = selected.has(rowId); // O(1)
selected.has(rowId) ? selected.delete(rowId) : selected.add(rowId);
```

Với bảng 10.000 dòng, mỗi lần tick checkbox bản array quét tới 10.000 phần tử; bản `Set` chỉ tốn một thao tác.

## 4. Đo, đừng đoán

Quy tắc số một của tối ưu: **đo trước khi sửa**. Trực giác về "chỗ nào chậm" rất hay sai. Trình duyệt cho bạn nhiều công cụ đo ngay trong JS.

### đo thời gian chính xác

`Date.now()` chỉ chính xác tới mili-giây và có thể bị "nhảy" khi đồng hồ hệ thống đổi. Dùng `performance.now()` (đơn vị mili-giây, độ phân giải dưới mili-giây, đơn điệu tăng) để đo đoạn code:

```ts
function measure<T>(label: string, fn: () => T): T {
  const start = performance.now();
  const result = fn();
  const ms = performance.now() - start;
  console.log(`${label}: ${ms.toFixed(2)}ms`);
  return result;
}

measure('sort 100k', () => bigArray.sort((a, b) => a - b));
```

### So sánh hai cách làm

Muốn biết `Set` có thật sự nhanh hơn `Array.includes` không, hãy đo trên dữ liệu đủ lớn:

```ts
const N = 100_000;
const data = Array.from({ length: N }, (_, i) => i);
const needles = Array.from({ length: 1_000 }, () => Math.floor(Math.random() * N));

measure('Array.includes', () => needles.filter((x) => data.includes(x)).length);

const set = new Set(data);
measure('Set.has', () => needles.filter((x) => set.has(x)).length);
// Set.has is usually hundreds to thousands of times faster at large N.
```

### và `performance.mark`

Cho đo nhanh, `console.time('x')` / `console.timeEnd('x')` tiện hơn. Cho phân tích sâu, `performance.mark()` + `performance.measure()` ghi mốc vào timeline của tab **Performance** trong DevTools, để bạn nhìn thấy đoạn code của mình nằm ở đâu giữa layout và paint.

```ts
performance.mark('filter:start');
const result = filterProducts(query);
performance.mark('filter:end');
performance.measure('filter', 'filter:start', 'filter:end');
```

## 5. "Chậm thuật toán" khác "chậm vì DOM"

Đây là điểm khiến tối ưu frontend khác hẳn tối ưu thuật toán thuần. Có **hai loại chậm** rất khác nhau:

1. **Chậm do tính toán (CPU/JS)** — vòng lặp `O(n²)`, parse JSON khổng lồ, sort sai cách. Sửa bằng thuật toán & cấu trúc dữ liệu (đúng trọng tâm series này).
2. **Chậm do render (layout, reflow, repaint)** — chạm vào DOM quá nhiều, đọc/ghi layout xen kẽ gây *layout thrashing*. Thuật toán "đẹp" nhưng vẫn lag vì bạn đụng DOM sai cách.

Ví dụ layout thrashing kinh điển — đọc `offsetHeight` (buộc trình duyệt tính layout) ngay sau khi ghi style, lặp lại trong vòng lặp:

```ts
// ❌ Each iteration: write style → read layout → forced sync reflow → O(n) reflows
for (const el of boxes) {
  el.style.height = 'auto';
  const h = el.offsetHeight; // read → browser must reflow immediately
  el.style.height = `${h * 2}px`;
}
```

```ts
// ✅ Split phases: read everything first, then write everything → 1 reflow
const heights = boxes.map((el) => el.offsetHeight); // batched reads
boxes.forEach((el, i) => {
  el.style.height = `${heights[i] * 2}px`; // batched writes
});
```

Cùng độ phức tạp `O(n)`, nhưng bản đầu chậm gấp nhiều lần vì ép trình duyệt reflow `n` lần. **Bài học**: khi UI lag, hãy mở tab Performance để biết thời gian nằm ở "Scripting" (thuật toán) hay "Rendering/Painting" (DOM) trước khi sửa.

## 6. Một checklist tư duy trước khi tối ưu

Trước khi viết một dòng tối ưu nào, hãy tự hỏi theo thứ tự này:

1. **Có thật sự chậm không?** Đo bằng `performance.now()` hoặc tab Performance. Đừng tối ưu cái không đo được.
2. **`n` lớn cỡ nào?** Với `n = 20`, `O(n²)` vẫn tức thì — đừng đánh đổi sự rõ ràng để tối ưu non. Tối ưu khi `n` thực sự lớn (hàng nghìn trở lên).
3. **Chậm vì CPU hay vì DOM?** Xem mục 5. Hai loại này sửa theo hai hướng khác nhau.
4. **Có thể làm ít việc hơn không?** Cache kết quả (Phần 7), chỉ render thứ đang nhìn thấy (Phần 4), gọi ít hơn (Phần 2).
5. **Có thể đổi cấu trúc dữ liệu không?** Thường đây là cú đòn rẻ nhất: `Array` → `Set`/`Map`.

> Nguyên tắc vàng: *"Làm cho nó chạy đúng, rồi mới làm cho nó nhanh — và chỉ làm nhanh chỗ đã đo là chậm."*

## Tóm tắt

- Frontend cần thuật toán vì ngân sách **16ms/khung hình** và vì code chạy trên máy người dùng, không scale được.
- Big-O trả lời câu hỏi: *gấp đôi dữ liệu thì tốn thêm bao nhiêu?* Cảnh giác vòng lặp lồng nhau và `find`/`includes` bên trong vòng lặp (`O(n²)`).
- Đổi `Array` sang `Set`/`Map` thường là cách rẻ nhất biến `O(n)` thành `O(1)`.
- Luôn **đo** bằng `performance.now()` / tab Performance trước khi sửa.
- Phân biệt "chậm thuật toán" (CPU) với "chậm vì DOM" (layout/repaint) — chúng cần cách sửa khác nhau.

**Phần tiếp theo:** Debounce, throttle & rate limiting — thuật toán đầu tiên hầu như app nào cũng cần, để một ô search không bắn 50 request mỗi giây.
