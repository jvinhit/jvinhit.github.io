## Kiến trúc clean (phân tầng)

Ý tưởng cốt lõi: **phụ thuộc hướng vào trong**. Domain (luật nghiệp vụ) không biết gì về Express, database, hay HTTP — đó là chi tiết bên ngoài phụ thuộc vào lõi, không bao giờ ngược lại.

```text
src/
├── presentation/    # controllers, routes, middleware (HTTP details)
├── application/     # use cases / services, DTOs, validators
├── domain/          # entities, interfaces, business rules (no framework!)
├── infrastructure/  # repositories, ORM, external APIs (implements domain interfaces)
└── shared/          # config, constants, utils
```

```ts
// domain/User.ts — pure business logic, zero dependencies
export class User {
  constructor(
    public readonly id: string | null,
    public readonly email: string,
    private readonly passwordHash: string,
    public readonly createdAt: Date,
  ) {}

  verifyPassword(plain: string): Promise<boolean> {
    return bcrypt.compare(plain, this.passwordHash);
  }
}

// application/RegisterUserService.ts — a use case orchestrating the domain
export class RegisterUserService {
  constructor(
    private readonly users: UserRepository,   // an interface, not a concrete class
    private readonly email: EmailService,
  ) {}

  async execute(email: string, password: string) {
    if (await this.users.findByEmail(email)) throw new AppError('Email already registered', 409);
    const user = new User(null, email, await bcrypt.hash(password, 10), new Date());
    await this.users.save(user);
    await this.email.sendWelcome(email);
    return { id: user.id, email: user.email };
  }
}

// presentation/AuthController.ts — only HTTP concerns
export class AuthController {
  constructor(private readonly registerUser: RegisterUserService) {}
  register = async (req: Request, res: Response, next: NextFunction) => {
    try {
      res.status(201).json(await this.registerUser.execute(req.body.email, req.body.password));
    } catch (err) { next(err); }
  };
}
```

Phần thưởng: bạn có thể đổi Postgres sang Mongo (chỉ viết lại infrastructure), hay Express sang Fastify (chỉ viết lại presentation), mà không chạm luật nghiệp vụ. Đây là mẫu repository + service từ Phase 6, đẩy tới kết luận hợp lý.

Cùng hình dạng này có nhiều tên — kiến trúc **Hexagonal / Ports & Adapters / Onion**. Domain định nghĩa **port** (interface); infrastructure cung cấp **adapter** (cài đặt cụ thể). Lõi chỉ phụ thuộc port, nên adapter cắm được.

### Từ vựng Domain-Driven Design

Khi domain phức tạp, **DDD** cho ngôn ngữ chung để mô hình hóa:

- có danh tính theo thời gian.
- định nghĩa bởi giá trị, bất biến.
- cụm đối tượng có một **root** giữ bất biến; tham chiếu aggregate khác bằng id.
- ranh giới rõ nơi một thuật ngữ có một nghĩa.
- code dùng đúng từ của chuyên gia nghiệp vụ.

> Ranh giới aggregate cũng là **ranh giới transaction** và đường nối tự nhiên để sau này tách thành service.

## Kiến trúc microservices

Một monolith trở nên khó scale và deploy quá một kích thước nhất định. Microservices chia nó thành các service deploy độc lập, mỗi cái sở hữu dữ liệu riêng.

```text
                ┌─────────────┐
   client ─────▶│ API Gateway │ (auth, rate-limit, routing — cross-cutting)
                └──────┬──────┘
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
  user-service   post-service   notif-service
        │             │             │
     user-db       post-db       notif-db   (a database per service)
```

```ts
// API Gateway — one entry point; cross-cutting concerns live here
import httpProxy from 'express-http-proxy';

app.use(authenticate);   // do auth/rate-limit/logging ONCE at the edge
app.use(rateLimit);
app.use('/api/users', httpProxy('http://user-service:3001'));
app.use('/api/posts', httpProxy('http://post-service:3002'));
```

Quan điểm senior thành thật: microservices đánh đổi độ phức tạp code lấy **độ phức tạp vận hành và hệ phân tán** (lỗi mạng, nhất quán cuối, distributed tracing). **Bắt đầu bằng monolith phân tầng tốt** (10.1) và tách service chỉ khi quy mô team hoặc áp lực scale đòi hỏi.

### Các mẫu hệ phân tán phải gọi tên được

- không có transaction ACID xuyên service, nên mô hình hóa workflow bằng chuỗi transaction cục bộ với **hành động bù** khi lỗi.
- ghi sự kiện vào bảng `outbox` trong cùng transaction rồi relay phát.
- mạng retry, nên mọi consumer phải xử lý cùng message hai lần an toàn.
- timeout, retry có backoff, và circuit breaker ở mọi lời gọi xuyên service.
- lan truyền trace id để theo dõi một request đầu-cuối.

## Kiến trúc hướng sự kiện

Thay vì service gọi nhau trực tiếp (gắn chặt), chúng **phát sự kiện** và bên khác **phản ứng**. Bên phát không biết và không quan tâm ai nghe.

```ts
import { EventEmitter } from 'node:events';

class DomainEventBus extends EventEmitter {
  publish(event: { type: string }) { this.emit(event.type, event); }
  subscribe(type: string, handler: (e: unknown) => void) { this.on(type, handler); }
}

// The register use case just announces what happened...
await this.users.save(user);
this.bus.publish({ type: 'UserRegistered', userId: user.id, email: user.email });

// ...and independent handlers react, each in its own module:
bus.subscribe('UserRegistered', (e) => emailService.sendWelcome(e.email));
bus.subscribe('UserRegistered', (e) => analytics.track('signup', e.userId));
```

Thêm "gửi cảnh báo Slack khi đăng ký" nghĩa là thêm *một subscriber mới* — không bao giờ chạm code đăng ký. Cho sự kiện xuyên service/bền, thay `EventEmitter` trong tiến trình bằng broker — **RabbitMQ**, Redis Streams, hoặc **Kafka**.

## CQRS

Tách mô hình **ghi** (command đổi trạng thái) khỏi mô hình **đọc** (query trả dữ liệu). Chúng có nhu cầu khác nhau — ghi cần validation và nhất quán; đọc cần tốc độ và denormalization.

```ts
class RegisterUserCommand { constructor(public email: string, public password: string) {} }

class RegisterUserHandler {
  constructor(private readonly users: UserRepository) {}
  handle(cmd: RegisterUserCommand) { return this.users.create({ email: cmd.email, password: cmd.password }); }
}

class CommandBus {
  private handlers = new Map<string, { handle: (c: unknown) => unknown }>();
  register(type: string, handler: { handle: (c: unknown) => unknown }) { this.handlers.set(type, handler); }
  execute(cmd: object) { return this.handlers.get(cmd.constructor.name)!.handle(cmd); }
}
```

CQRS hợp tự nhiên với hệ hướng sự kiện và event sourcing, nhưng thêm phức tạp — dùng cho **domain phức tạp** có tải đọc/ghi bất đối xứng, không phải CRUD đơn giản.

> **Event sourcing** đi xa hơn: thay vì lưu trạng thái hiện tại, lưu **log sự kiện chỉ-thêm** và dựng lại trạng thái bằng cách phát lại. Bạn được audit trail hoàn hảo và du hành thời gian, đổi lại phải version sự kiện và dựng read projection. Mạnh, nhưng chỉ dùng khi domain thật sự cần lịch sử.

## Design pattern cốt lõi

```ts
// Singleton — one shared instance (DB connection, config)
class Database {
  private static instance: Database;
  static getInstance(): Database { return (this.instance ??= new Database()); }
}

// Factory — create objects without hard-coding the concrete class
class PaymentGatewayFactory {
  static create(type: 'stripe' | 'paypal'): PaymentGateway {
    if (type === 'stripe') return new StripeGateway();
    if (type === 'paypal') return new PayPalGateway();
    throw new Error(`Unknown gateway: ${type}`);
  }
}

// Observer — the EventEmitter / pub-sub pattern (10.3)
// Decorator — wrap behavior (e.g. logging) without changing the original
function withLogging<T extends (...a: never[]) => Promise<unknown>>(fn: T, name: string): T {
  return (async (...args) => {
    logger.info(`→ ${name}`);
    const result = await fn(...args);
    logger.info(`← ${name}`);
    return result;
  }) as T;
}
```

Senior dùng pattern để **đặt tên và tái dùng một giải pháp đã được kiểm chứng** — không bao giờ để tỏ ra thông minh. Pattern sai còn tệ hơn không có.

## Nguyên tắc SOLID

Năm nguyên tắc nền cho mọi thứ ở trên:

- Một lý do để đổi. `User` giữ dữ liệu; `UserRepository` lưu; `EmailService` gửi email — không phải một god-class làm cả ba.
- Mở để mở rộng, đóng để sửa. Thêm `PaymentGateway` mới mà không sửa `PaymentProcessor`.
- Mọi subtype `PaymentGateway` phải chạy được ở nơi mong đợi base.
- Nhiều interface nhỏ, tập trung tốt hơn một interface to.
- Phụ thuộc trừu tượng, không phải cụ thể:

```ts
// ✅ OrderService depends on the abstraction — that's why DI (Phase 6) and
//    clean architecture (10.1) work. SOLID is the foundation of it all.
class OrderService {
  constructor(private readonly gateway: PaymentGateway) {}
  processOrder(order: Order) { return this.gateway.pay(order.amount); }
}
```

Để ý mọi thứ kết nối: DI, repository/service, clean architecture, và khả năng test đều là *hệ quả* của SOLID.

## Bạn đã tới đích — tư duy Super Senior

Mười phase, từ event loop tới kiến trúc enterprise. Nhưng dấu hiệu thật của super senior không phải API thuộc lòng — mà là **phán đoán**:

- Bạn dựng app chuẩn production mà không liên tục tra docs.
- Bạn **đánh đổi có hiểu biết** — và bảo vệ được.
- Bạn tối ưu *sau khi* đo, bảo mật mặc định, và test để thay đổi không sợ.
- Bạn biết **khi nào không** dùng một pattern — kỹ năng senior hiếm nhất.
- Bạn dìu dắt người khác, dẫn dắt thảo luận kỹ thuật, và ra quyết định kiến trúc.

> Lời kết của curriculum vẫn đúng: con đường này **đòi hỏi kỷ luật và thực hành đều đặn. Tập trung chiều sâu, không chỉ chiều rộng**. Đọc mười phase này khiến bạn có kiến thức. *Dựng* các dự án trong từng phase mới khiến bạn thành Super Senior.
