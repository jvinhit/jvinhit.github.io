Frontend hiện đại dựa vào rất nhiều thư viện bên thứ ba: thanh toán (Stripe), phân tích (GA, Mixpanel), bản đồ, storage, auth. Vấn đề là: nếu code của bạn gọi thẳng API của chúng ở khắp nơi, bạn bị **buộc cứng** vào chúng — đổi nhà cung cấp = sửa hàng trăm chỗ. **Facade** và **Adapter** là hai pattern bảo vệ bạn khỏi điều đó.

---

## 1. Một cửa sổ sạch trước hệ thống phức tạp

Facade cung cấp **một giao diện đơn giản** che đi sự phức tạp bên trong. Người dùng facade không cần biết có bao nhiêu bước, bao nhiêu API con phía sau.

Ví dụ: phân tích (analytics) thường cần khởi tạo, set user, gửi event với cấu trúc cụ thể. Rải các lời gọi đó khắp app là ác mộng bảo trì.

```ts
// ❌ component calls SDK directly with details exposed everywhere
import mixpanel from 'mixpanel-browser';
mixpanel.init('TOKEN', { debug: true });
mixpanel.track('Button Clicked', { button_id: 'checkout', $current_url: location.href });
// ...repeated with different syntax in 50 places
```

Facade gom tất cả vào một giao diện gọn, theo ngôn ngữ của *domain* chứ không phải của SDK:

```ts
// analytics.ts — Facade: app only sees this interface
class Analytics {
  private initialized = false;

  init(token: string): void {
    mixpanel.init(token, { debug: import.meta.env.DEV });
    this.initialized = true;
  }

  identify(userId: string, traits?: Record<string, unknown>): void {
    if (!this.initialized) return; // facade handles defensive checks too
    mixpanel.identify(userId);
    if (traits) mixpanel.people.set(traits);
  }

  // domain-named, not SDK-named — reads as business intent
  trackCheckout(orderId: string, total: number): void {
    if (!this.initialized) return;
    mixpanel.track('Checkout Completed', { order_id: orderId, total, url: location.href });
  }
}

export const analytics = new Analytics();
```

```ts
// usage site: clean, domain-oriented, no Mixpanel details leaking
analytics.trackCheckout('order-123', 499000);
```

Lợi ích: gọi sạch hơn, **phòng thủ tập trung** (kiểm tra `initialized` một chỗ), và đặt nền để đổi nhà cung cấp — dẫn tới Adapter.

## 2. Làm cho hai giao diện không khớp "nói chuyện được"

Adapter biến giao diện của một thư viện thành giao diện mà code của bạn **mong đợi**. Nó là "đầu chuyển đổi" giữa interface của bạn và interface của bên thứ ba.

Tình huống kinh điển: bạn muốn đổi từ Mixpanel sang Google Analytics, hoặc hỗ trợ cả hai. Nếu định nghĩa **một interface chung** và viết adapter cho từng nhà cung cấp, phần còn lại của app không cần biết đang dùng cái nào.

```ts
// Shared interface YOU define — app only depends on this
interface AnalyticsProvider {
  identify(userId: string): void;
  track(event: string, props?: Record<string, unknown>): void;
}

// Adapter 1: wrap Mixpanel to match the shared interface
class MixpanelAdapter implements AnalyticsProvider {
  constructor(token: string) {
    mixpanel.init(token);
  }
  identify(userId: string): void {
    mixpanel.identify(userId);
  }
  track(event: string, props?: Record<string, unknown>): void {
    mixpanel.track(event, props);
  }
}

// Adapter 2: wrap Google Analytics — same interface, very different internals
class GoogleAnalyticsAdapter implements AnalyticsProvider {
  identify(userId: string): void {
    gtag('set', { user_id: userId });
  }
  track(event: string, props?: Record<string, unknown>): void {
    gtag('event', event, props); // GA uses different syntax; adapter hides the difference
  }
}
```

Giờ đổi nhà cung cấp chỉ là đổi **một dòng** nơi tạo provider — phần còn lại của app không hề hay biết:

```ts
// Factory (Part 4) picks the adapter; app uses the shared interface
const analytics: AnalyticsProvider = import.meta.env.PROD
  ? new GoogleAnalyticsAdapter()
  : new MixpanelAdapter('dev-token');

analytics.track('page_view'); // don't care which provider is underneath
```

Đây chính là **chống vendor lock-in** thành hình, và là nguyên lý Dependency Inversion (Phần 1): app phụ thuộc vào *trừu tượng* (`AnalyticsProvider`), không phải *chi tiết* (Mixpanel/GA).

## 3. Phân biệt cho rõ

Hai pattern này dễ lẫn vì cùng "bọc thứ khác". Khác biệt nằm ở **mục đích**:

| | Facade | Adapter |
|---|--------|---------|
| Mục đích | **simplify** a complex system | **convert** one interface to another |
| What's underneath | usually many APIs/steps → one door | one library → match your interface |
| Swappable implementations? | not the main goal | **that is** the goal (many adapters, one interface) |
| Question it answers | "how do I use this more easily?" | "how does this fit my system?" |

Thực tế chúng thường đi cùng nhau: một **Facade** lộ ra giao diện sạch, bên trong dùng **Adapter** để chọn nhà cung cấp.

## 4. Ứng dụng thực tế: trừu tượng hóa storage

Một ví dụ gần gũi: bạn cần lưu trữ, nhưng tùy ngữ cảnh dùng `localStorage`, `sessionStorage`, hoặc IndexedDB, hoặc bộ nhớ tạm (cho SSR/test). Định nghĩa một interface, adapter cho từng backend:

```ts
interface Storage {
  get<T>(key: string): T | null;
  set<T>(key: string, value: T): void;
  remove(key: string): void;
}

class LocalStorageAdapter implements Storage {
  get<T>(key: string): T | null {
    const raw = localStorage.getItem(key);
    return raw ? (JSON.parse(raw) as T) : null;
  }
  set<T>(key: string, value: T): void {
    localStorage.setItem(key, JSON.stringify(value));
  }
  remove(key: string): void {
    localStorage.removeItem(key);
  }
}

// In-memory adapter — for tests/SSR where localStorage isn't available
class MemoryStorageAdapter implements Storage {
  private store = new Map<string, unknown>();
  get<T>(key: string): T | null {
    return (this.store.get(key) as T) ?? null;
  }
  set<T>(key: string, value: T): void {
    this.store.set(key, value);
  }
  remove(key: string): void {
    this.store.delete(key);
  }
}
```

Code nghiệp vụ chỉ phụ thuộc `Storage`. Test thì tiêm `MemoryStorageAdapter`, không cần mock `localStorage` toàn cục — sạch và đáng tin hơn nhiều.

## 5. Khi nào KHÔNG dùng

- Thư viện đã có giao diện sạch và bạn chắc không đổi nó → bọc thêm một tầng chỉ thêm gián tiếp vô ích.
- Adapter "tiên tri": dựng abstraction cho nhà cung cấp thứ hai mà bạn *có thể* dùng trong tương lai → đây là over-engineering. Chỉ trừu tượng khi nhu cầu đổi/đa nhà cung cấp **thật sự** xuất hiện (YAGNI).
- Cân bằng: bọc những phụ thuộc **rủi ro cao** (dễ đổi, lan rộng, khó test); để yên những phụ thuộc ổn định, cục bộ.

---

## Tóm tắt

- **Facade** đơn giản hóa một hệ thống phức tạp sau một giao diện sạch, theo ngôn ngữ domain; tập trung cả phòng thủ.
- **Adapter** chuyển interface của thư viện về interface *của bạn* → nhiều nhà cung cấp dùng chung một giao diện, chống vendor lock-in (Dependency Inversion).
- Chúng thường đi cùng: Facade lộ giao diện, Adapter chọn cài đặt; Factory (Phần 4) chọn adapter.
- Đừng trừu tượng "phòng xa" — chỉ bọc khi nhu cầu đổi/đa nhà cung cấp thật sự đến.

**Phần tiếp theo:** Decorator & Proxy — thêm hành vi (logging, cache, lazy, reactive) mà không sửa đối tượng gốc.
