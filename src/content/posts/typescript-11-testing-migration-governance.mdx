Compiler không test behavior; unit test không test inference; lint không chứng minh domain invariant. Quality system tốt biết mỗi công cụ chịu trách nhiệm cho lớp lỗi nào.

## Kim tự tháp kiểm chứng

| Lớp                  | Bắt lỗi gì                                 | Ví dụ                        |
| -------------------- | ------------------------------------------ | ---------------------------- |
| Compiler             | assignability, exhaustiveness, nullability | sai payload event            |
| Type test            | public inference và invalid calls          | overload regression          |
| Unit/property test   | runtime logic và invariant                 | parser, state transition     |
| Integration/contract | boundary thật                              | API/schema/database adapter  |
| E2E                  | critical user flow                         | checkout                     |
| Lint                 | unsafe pattern compiler không cấm          | floating promise, unsafe any |

Không snapshot hover type dài. Assert capability consumer thật sự cần.

## Negative type test là bắt buộc cho guardrail

```ts
declare const client: Client;

await client.getUser('usr_1');

// @ts-expect-error invalid ID shape must stay rejected
await client.getUser(123);
```

Nếu chỉ test positive, API có thể widen thành `any` mà suite vẫn xanh.

## Migration theo boundary, không theo phần trăm file

Một chiến lược incremental:

1. Bật `allowJs` + `checkJs` cho vùng phù hợp.
2. Đưa input ngoài hệ thống về `unknown` trong adapter.
3. Tạo domain types và contract cho feature đang thay đổi.
4. Convert leaf module trước, orchestration sau.
5. Siết rule theo directory mới; legacy có budget giảm dần.
6. Chỉ bật strict flag toàn repo khi error category đã có playbook.

“90% file là `.ts`” không nói hệ thống an toàn nếu 10% boundary vẫn trả `any`.

## Any budget

Phân loại thay vì cấm khẩu hiệu:

- explicit `any` do mình viết;
- implicit `any`;
- unsafe assignment/call/member access từ dependency;
- assertion và non-null assertion;
- suppression (`@ts-ignore`).

Mỗi suppression cần lý do, owner và điều kiện xóa. Dùng `@ts-expect-error` thay `@ts-ignore` để compiler báo khi workaround hết cần.

## Nâng TypeScript như một migration sản phẩm

1. Đọc release notes và breaking changes.
2. Tạo branch chỉ nâng compiler/`@types`, không trộn feature.
3. Chạy full type tests và declaration consumer fixtures.
4. Phân loại error: bug thật, inference đổi, lib.d.ts đổi, config deprecation.
5. Sửa bằng explicit contract trước assertion.
6. Canary trên một package/app rồi mở rộng.
7. Ghi minimum supported TS version cho library.

TypeScript 6 có deprecation hướng tới TypeScript 7 native. `ignoreDeprecations` chỉ là cầu tạm, không phải kết quả migration.

## Contract test tại boundary

Schema consumer test nên chạy trên fixture từ producer hoặc generated spec. Nếu nhiều service, thêm compatibility check vào pipeline producer để biết thay đổi nào phá consumer trước deploy.

## Governance không làm chậm team

Guardrail tốt tự động và gần feedback loop:

- editor dùng workspace TypeScript version;
- pre-commit chỉ chạy fast affected checks;
- PR chạy typecheck/lint/unit/type tests;
- main/nightly chạy full graph, package fixture, diagnostics;
- dashboard theo dõi any/suppression và check-time trend.

## Lab

1. Viết test matrix cho một library: runtime + positive type + negative type + tarball consumer.
2. Lập inventory `any`/assertion/suppression và tạo baseline budget.
3. Migrate một vertical slice từ request tới domain, không chỉ đổi extension.
4. Dry-run nâng compiler, ghi taxonomy lỗi và playbook.

**Done khi:** quality gate bắt regression cả runtime lẫn type UX, còn migration giảm risk theo boundary mà feature delivery vẫn tiếp tục.
