Phần 3 nhắc tới live regions. Phần này đào sâu một trong những phần khó nhất của a11y động: làm sao báo cho người dùng screen reader biết điều **xảy ra mà không do họ trực tiếp gây ra** — kết quả tìm kiếm cập nhật, toast "Đã lưu", lỗi form, route đổi trong SPA. Không có thông báo, người mù đơn giản là *không biết* có gì vừa thay đổi.

> Live region là một vùng DOM mà screen reader **theo dõi**; khi nội dung bên trong đổi, AT đọc thay đổi đó — kể cả khi focus đang ở chỗ khác.

---

## 1. Cơ chế: vùng phải tồn tại TRƯỚC khi đổi

Cạm bẫy số một: live region phải có mặt trong DOM **trước**, rồi bạn *cập nhật nội dung* của nó. Chèn cả một phần tử `aria-live` đã có sẵn text thường không được đọc.

```html
<!-- ✅ Vùng rỗng có sẵn từ đầu; sau đó JS đổi text bên trong -->
<div id="sr-status" aria-live="polite" class="sr-only"></div>
```

```js
function announce(message) {
  const region = document.getElementById('sr-status');
  region.textContent = '';                 // reset để cùng text vẫn được đọc lại
  requestAnimationFrame(() => { region.textContent = message; });
}
```

`.sr-only` ẩn thị giác nhưng vẫn lộ cho AT (không dùng `display:none` — sẽ bị loại khỏi cây a11y, Part 1).

## 2. polite vs assertive — và role tương đương

`aria-live` có hai mức dùng thực tế:

| `aria-live` | Role tương đương | Khi nào | Hành vi |
|---|---|---|---|
| `polite` | `role="status"` | thông tin không khẩn (đã lưu, X kết quả) | đọc khi AT rảnh, không ngắt |
| `assertive` | `role="alert"` | khẩn (lỗi, mất kết nối) | **ngắt** ngay lời đang đọc |

```html
<!-- Hai cách viết tương đương -->
<div aria-live="polite"></div>
<div role="status"></div>           <!-- = polite + aria-atomic ngầm -->

<div aria-live="assertive"></div>
<div role="alert"></div>            <!-- = assertive; dùng cho lỗi -->
```

> Dùng `assertive`/`alert` **tiết kiệm**. Lạm dụng làm screen reader liên tục ngắt lời, gây khó chịu và mất ngữ cảnh. Mặc định nên là `polite`.

## 3. aria-atomic & aria-relevant

Hai thuộc tính tinh chỉnh *cái gì* được đọc khi vùng đổi:

```html
<!-- aria-atomic="true": đọc TOÀN BỘ vùng, không chỉ phần đổi -->
<div aria-live="polite" aria-atomic="true">
  Còn lại <span id="time">5:00</span>
</div>
<!-- khi #time đổi → đọc cả "Còn lại 4:59", không chỉ "4:59" -->

<!-- aria-relevant: loại thay đổi nào đáng đọc (mặc định "additions text") -->
<div aria-live="polite" aria-relevant="additions"></div>
```

`role="status"`/`role="alert"` đã ngầm `aria-atomic="true"`. Với log chỉ thêm dòng (chat), dùng `role="log"` (atomic=false, chỉ đọc dòng mới).

## 4. Toast & hàng đợi thông báo

Toast là ca điển hình cần live region — nhưng nhiều toast dồn dập sẽ chồng chéo. Pattern tốt: một vùng `polite` duy nhất, dồn thông báo tuần tự.

```js
class Announcer {
  #region = document.getElementById('sr-status');
  #queue = [];
  #busy = false;

  announce(msg) { this.#queue.push(msg); this.#flush(); }

  async #flush() {
    if (this.#busy || !this.#queue.length) return;
    this.#busy = true;
    this.#region.textContent = '';
    await new Promise((r) => requestAnimationFrame(r));
    this.#region.textContent = this.#queue.shift();
    // chừa thời gian để SR đọc xong trước thông báo kế
    setTimeout(() => { this.#busy = false; this.#flush(); }, 1000);
  }
}
```

Toast hiển thị thị giác (nút đóng, tự ẩn) tách biệt với *thông báo SR*: phần nhìn dùng UI bình thường, phần đọc đi qua live region. Đừng cho toast tự biến mất quá nhanh nếu nó chứa hành động (WCAG 2.2.1 thời gian).

## 5. Thông báo khi đổi route trong SPA

Khi điều hướng trong SPA, không có full page load → screen reader **không tự thông báo** trang mới. Bạn phải tự làm hai việc:

```js
function onRouteChange(newTitle) {
  document.title = newTitle;              // 1. cập nhật <title>

  // 2. thông báo + chuyển focus về đầu nội dung mới
  announce(`Đã chuyển tới ${newTitle}`);   // live region polite
  const heading = document.querySelector('main h1, main h2');
  heading?.setAttribute('tabindex', '-1');
  heading?.focus();                        // focus về heading mới (không cuộn giật → preventScroll nếu cần)
}
```

```text
Sau điều hướng SPA, làm đủ:
  ① đổi document.title
  ② chuyển focus tới heading/landmark của trang mới (hoặc một "skip target")
  ③ (tùy chọn) announce tên trang qua live region
```

Chuyển focus quan trọng hơn cả announce: nó vừa báo vị trí mới vừa đặt điểm bắt đầu cho phím Tab.

## 6. aria-busy & trạng thái đang tải

Khi một vùng đang cập nhật nhiều phần, đặt **`aria-busy="true"`** để screen reader *chờ* đọc cho tới khi xong — tránh đọc trạng thái nửa vời.

```js
const list = document.getElementById('results');
list.setAttribute('aria-busy', 'true');   // bắt đầu tải
await fillResults(list);
list.setAttribute('aria-busy', 'false');  // xong → SR đọc kết quả gọn
announce(`${count} kết quả`);              // thông báo tổng kết
```

Với spinner: đặt `role="status"` + text ẩn "Đang tải…" để người mù biết có gì đang chạy; xóa khi xong. Đừng để spinner câm lặng.

---

## 7. Tóm tắt

- Live region phải **tồn tại trong DOM trước**, rồi mới *đổi nội dung*; ẩn bằng `.sr-only`, không `display:none`.
- `polite`/`role="status"` cho thông tin thường (mặc định); `assertive`/`role="alert"` cho khẩn cấp — **dùng tiết kiệm**.
- `aria-atomic="true"` đọc cả vùng; `role="log"` cho luồng chỉ thêm dòng (chat).
- Toast: một vùng polite + **hàng đợi tuần tự**, tách phần nhìn khỏi phần đọc SR.
- Đổi route SPA: cập nhật `<title>` + **chuyển focus** về heading mới + (tùy chọn) announce.
- `aria-busy="true"` trong khi cập nhật để SR không đọc trạng thái dở; spinner luôn có text trạng thái cho AT.

**Phần tiếp theo:** Accessible drag-and-drop & reordering — cung cấp giải pháp thay thế bàn phím (WCAG 2.2 Dragging Movements), điều khiển bằng pointer, và thông báo tiến trình kéo-thả qua live region.
