## 1. Lighthouse — điểm khởi đầu (lab)

Lighthouse (trong DevTools, tab Lighthouse, hoặc `npx lighthouse`) chạy một bài kiểm tra mô phỏng và cho điểm 0–100 cùng danh sách gợi ý. Đây là cách nhanh nhất để có cái nhìn tổng quan.

```bash
# Run Lighthouse from CLI, export JSON report for comparison/CI
npx lighthouse https://example.com --output=json --output-path=./report.json \
  --only-categories=performance --throttling-method=simulate
```

**Hiểu đúng về Lighthouse**: nó là **lab data** — chạy trên một cấu hình mô phỏng cố định. Cực hợp để *chẩn đoán* ("gợi ý nào đáng làm") và *theo dõi hồi quy trong CI*, nhưng điểm số **không** phải trải nghiệm người dùng thật. Đừng bị ám ảnh kéo điểm lên 100; hãy nhìn các *cơ hội* (opportunities) cụ thể nó liệt kê.

Lighthouse cũng cho **TBT** thay cho INP (vì lab không có tương tác thật) và **CLS lab** (chỉ tính trong lúc load). Đây là proxy, không thay được field data.

## 2. Tab Performance — chẩn đoán sâu (lab)

Khi Lighthouse nói "có long task" hay "LCP chậm" nhưng không rõ *vì sao*, tab **Performance** của DevTools cho bạn dòng thời gian chi tiết: từng task JS, layout, paint, network.

Quy trình profile chuẩn:

1. Mở tab Performance, bật **CPU: 4× slowdown** và **Network: Slow 4G** (giả lập máy phổ thông — bước quan trọng nhất).
2. Bấm **Record**, tải lại trang hoặc thực hiện tương tác cần đo, dừng record.
3. Read:
**Main thread**: thanh dài màu (long task > 50ms có gạch đỏ) = thủ phạm INP/TBT.
**Mốc LCP/FCP**: hiển thị trên timeline để biết khi nào nội dung hiện.
**Layout Shift**: các vạch đánh dấu shift = thủ phạm CLS.

> Mẹo: dùng `performance.mark()` / `performance.measure()` (Phần 1) để gắn nhãn đoạn code của bạn — chúng hiện ngay trên timeline, giúp định vị code của mình giữa rừng task của trình duyệt.

## 3. CrUX — sự thật từ người dùng Chrome (field)

**Chrome User Experience Report (CrUX)** là dữ liệu field do Google thu từ người dùng Chrome thật trên hàng triệu site. Đây là *chính nguồn* Google dùng để xếp hạng CWV.

Cách truy cập:

- **PageSpeed Insights** (pagespeed.web.dev): nhập URL → thấy cả CrUX (field, phần trên) lẫn Lighthouse (lab, phần dưới) cạnh nhau. Cách nhanh nhất để so field vs lab.
- **CrUX API / BigQuery**: lấy dữ liệu theo chương trình cho dashboard.
- **Search Console**: báo cáo Core Web Vitals theo nhóm URL.

Hạn chế: CrUX chỉ có với site đủ lưu lượng, dữ liệu gộp theo 28 ngày (chậm phản ánh thay đổi), và chỉ người dùng Chrome. Để có dữ liệu *tức thì* và *của riêng bạn*, cần RUM.

## 4. RUM — đo người dùng thật của riêng bạn (field)

**Real User Monitoring (RUM)** là tự thu chỉ số từ chính người dùng của bạn. Ưu điểm so với CrUX: tức thì, mọi trình duyệt, và cắt lát được theo thiết bị/quốc gia/route/phiên bản. Dựng RUM tối giản với `web-vitals` (Phần 2):

```ts
import { onLCP, onINP, onCLS, onTTFB, onFCP } from 'web-vitals';

interface VitalPayload {
  name: string;
  value: number;
  rating: string;
  id: string;
  path: string;
  conn?: string; // connection type, for slicing by network
}

function report(metric: { name: string; value: number; rating: string; id: string }) {
  const payload: VitalPayload = {
    ...metric,
    path: location.pathname,
    conn: (navigator as Navigator & { connection?: { effectiveType?: string } }).connection
      ?.effectiveType,
  };
  // sendBeacon works even when the tab is closing — no data loss on page exit
  navigator.sendBeacon('/rum', JSON.stringify(payload));
}

[onLCP, onINP, onCLS, onTTFB, onFCP].forEach((fn) => fn(report));
```

Phía server gom lại, tính **p75 theo route** để biết trang nào đang tệ với người dùng thật. Đây là vòng lặp phản hồi quan trọng nhất: deploy → đo field → thấy chỗ tệ → sửa → đo lại.

> Quan trọng: tính p75, **không** phải trung bình (Phần 2). Và cắt lát theo `conn`/thiết bị để phát hiện "nhanh trên desktop, tệ trên mobile".

## 5. WebPageTest — phân tích chuyên sâu (lab nâng cao)

`webpagetest.org` chạy test trên thiết bị/mạng thật ở nhiều vị trí địa lý, cho **waterfall** chi tiết từng request, **filmstrip** (chuỗi ảnh chụp quá trình tải), và so sánh nhiều URL cạnh nhau. Khi cần hiểu *thứ tự tải tài nguyên* và *điều gì chặn điều gì*, đây là công cụ mạnh nhất.

Dùng filmstrip để thấy chính xác khoảnh khắc LCP hiện, và waterfall để phát hiện request nào đến muộn/chặn render (dẫn vào Phần 4 về critical rendering path).

---

## 6. Chọn công cụ theo câu hỏi

| Câu hỏi của bạn | Công cụ |
|------------------|---------|
| Trang tôi nhanh với người dùng thật không? | **CrUX / RUM** (field) |
| Trang nào/route nào đang tệ? | **RUM** (slice by path) |
| Vì sao nó chậm? (chẩn đoán) | **Performance tab**, **WebPageTest** |
| Có cơ hội tối ưu nào dễ? | **Lighthouse** |
| Có bị hồi quy sau deploy không? | **Lighthouse CI** + **RUM alert** |

> Nguyên tắc: **field data quyết định *có vấn đề không* và *ở đâu*; lab data giúp *hiểu vì sao* và *sửa thế nào*.** Cả hai bổ trợ, không thay thế nhau.

---

## Tóm tắt

- **Lighthouse** (lab): tổng quan + cơ hội tối ưu + CI; đừng ám ảnh điểm 100, nhìn opportunities.
- **Tab Performance** (lab): chẩn đoán sâu long task/LCP/CLS; luôn throttle CPU 4× + Slow 4G.
- **CrUX** (field): sự thật từ người dùng Chrome, là nguồn xếp hạng; xem nhanh qua PageSpeed Insights.
- **RUM** tự dựng (field): tức thì, mọi trình duyệt, cắt lát theo route/thiết bị; tính **p75**, dùng `sendBeacon`.
- **WebPageTest**: waterfall + filmstrip cho phân tích thứ tự tải.

**Phần tiếp theo:** Critical rendering path — hành trình từ HTML tới pixel, và những gì chặn render.
